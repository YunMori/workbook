## Ⅰ. 객관식 해설

**1. 정답 ③** — `const`는 선언 시 반드시 초기값을 설정해야 한다. 생략하면 `'const' declarations must be initialized.` 에러가 발생한다. (DOM_Event §2)

**2. 정답 ①** — 자동 형변환 규칙에서 String은 빈 문자열 `''`만 `false`이고 나머지는 모두 `true`다. 따라서 `'0'`은 `true`. (DOM_Event §3)

**3. 정답 ④** — `for...in`은 배열 반복자가 아닌 **속성 열거**를 사용하므로 인덱스가 출력된다. 값을 얻으려면 `for...of`를 써야 한다. (실행 검증 완료) (DOM_Event §6)

**4. 정답 ②** — `currentTarget`은 핸들러가 연결된 요소를 참조하며 일반 함수 콜백의 `this`와 같다. ①④는 `target`에 대한 설명이고, ③은 틀리다(이벤트가 처리되는 동안에만 사용 가능). (DOM_Event §9)

**5. 정답 ③** — 일반 함수 콜백의 `this`는 이벤트가 부착된 요소를 가리키지만, 화살표 함수는 자신의 `this`를 갖지 않아 상위 스코프(`window`)를 따른다. (DOM_Event §9 참고)

**6. 정답 ①** — `v-on`(Name) `:submit`(Argument) `.prevent`(Modifiers) `="onSubmit"`(Value). (Basic_Syntax — Directive 전체 구문)

**7. 정답 ④** — `v-show`는 항상 DOM에 렌더링되고 CSS `display`만 전환한다. `v-else`와 함께 쓸 수 없고, 초기 렌더링 비용이 높으며 토글 비용이 낮다. (Basic_Syntax — Conditional Rendering)

**8. 정답 ②** — `isActive`가 `false`이므로 `active`는 빠지고, `hasInfo`가 `true`이므로 `text-primary`가 붙는다. 일반 `class="static"`은 그대로 병합된다. (Basic_Syntax — Binding HTML Classes)

**9. 정답 ①** — 동일 요소에서 `v-if`가 `v-for`보다 우선순위가 높아 `v-if` 조건이 `v-for` 범위 변수(`todo`)에 접근할 수 없다. 해결책은 `computed` 활용 또는 `<template v-for>`로 `v-if` 위치 이동. (Basic_Syntax — v-for와 v-if)

**10. 정답 ③** — IME(Input Method Editor) 동작 방식과 `v-model`의 양방향 바인딩 방식이 상충한다. 한국어·중국어·일본어 등은 `v-bind` + `v-on` 조합을 사용해야 한다. (Basic_Syntax — v-model / 참고: IME)

**11. 정답 ④** — CSR 단점은 ㄱ(느린 초기 로드), ㄷ(SEO 문제). ㄴ과 ㄹ은 오히려 CSR의 **장점**이다(새로고침이 발생하지 않음, Frontend/Backend 명확한 분리). (Introduction_of_Vue §1-2)

**12. 정답 ②** — SFC의 최상위 언어 블록은 `<template>`, `<script>`, `<style>` 세 가지다. (Introduction_of_Vue §4-2)

**13. 정답 ③** — JavaScript에서는 일반 변수의 접근·변형을 감지할 방법이 없기 때문에, 의존성 추적 기반 반응형 시스템을 구현하려고 참조 자료형(객체)으로 래핑한 것이다. (Introduction_of_Vue p.54)

**14. 정답 ①** — `node_modules`는 `.gitignore`에 작성되며, 필요할 때 `npm install`로 재생성하므로 Git 관리 대상이 아니다. (Introduction_of_Vue §8, §14)

**15. 정답 ④** — 자식으로 전달할 때는 HTML 속성 표기법과 동일하게 **kebab-case**, 선언(`defineProps`) 및 템플릿 참조 시에는 **camelCase**. (component_state_flow §1-3)

**16. 정답 ②** — `computed`는 의존된 반응형 데이터를 기반으로 캐시되고 의존 데이터가 변경될 때만 재평가된다. `method`는 다시 렌더링될 때마다 항상 실행된다. (component_state_flow §3-2)

**17. 정답 ③** — 이벤트 선언·발신은 camelCase(`emit('someEvent')`), 부모에서 수신은 kebab-case(`@some-event`). (component_state_flow §2-5)

**18. 정답 ①** — `reverse()`와 `sort()`는 원본 배열을 변경하므로 `computed` 안에서는 반드시 복사본을 만들어 사용한다: `[...numbers].reverse()`. (component_state_flow §4-3)

**19. 정답 ④** — `store`는 중앙 저장소 자체이며 `watch()`와 대응되지 않는다. Pinia의 매핑은 `state === ref()`, `getters === computed()`, `actions === function()`. (state_management §2)

**20. 정답 ④** — `setTimeout`은 Web API로 위임되므로 `Hi` → `Bye` 출력 후, 3초 뒤 Task Queue를 거쳐 `Work`가 출력된다. (실행 검증 완료) (Asynchronous_JavaScript — 런타임의 시각적 표현)

**21. 정답 ②** — Promise는 "작업이 끝나면 실행시켜 줄게"라는 약속으로, 성공에 대한 약속은 `then()`, 실패에 대한 약속은 `catch()`다. Promise를 쓴다고 JavaScript가 multi-thread가 되지는 않는다. (Asynchronous_JavaScript — Promise)

## Ⅱ. 주관식 해설

**22.** `v-bind` → **`:`** (colon) / `v-on` → **`@`**
※ 예: `:src="imageSrc"`, `@click="myFunc"`

**23.** `40`, `40`
- 참조 자료형은 **주소가 복사**되므로 `obj1`과 `obj2`가 같은 객체를 가리킨다. `obj2.age`를 바꾸면 `obj1.age`도 함께 바뀐다. (실행 검증 완료)

**24.** `numbers.value.filter((number) => number % 2 === 0)`
- `<script>` 내부이므로 `.value`가 필요하다. `filter()`는 원본을 수정하지 않고 새 배열을 반환한다.

**25.** `state`, `getters`, `actions`
- 각각 `ref()`, `computed()`, `function()`에 대응한다.

**26.** `RouterLink` / `RouterView`
- `RouterLink`: 페이지를 다시 로드하지 않고 URL을 변경하며 HTML `<a>` 태그를 렌더링
- `RouterView`: `RouterLink`의 URL에 해당하는 컴포넌트를 표시

**27.**
- `forEach()` — 반환 값이 **없다(`undefined`)**. 각 요소에 대해 콜백을 호출만 한다.
- `map()` — 각 요소에 대한 **콜백 결과를 모은 새로운 배열**을 반환한다.

## Ⅲ. 서술형 채점 기준

**28. (5점)**

| 배점 | 채점 요소 |
|---|---|
| 2점 | `v-if`는 조건이 false면 요소를 렌더링하지 않고(DOM에서 제거), `v-show`는 항상 DOM에 렌더링하고 CSS `display`만 전환한다 |
| 2점 | `v-if` = cheap initial load / expensive toggle, `v-show` = expensive initial load / cheap toggle |
| 1점 | 콘텐츠를 매우 자주 전환하면 `v-show`, 실행 중 조건이 거의 변하지 않으면 `v-if` 권장 |

**모범 답안**
> `v-if`는 표현식의 참/거짓에 따라 요소를 **조건부로 렌더링**하며, 초기 조건이 false면 아무 작업도 하지 않는다. 반면 `v-show`는 초기 조건과 관계없이 **항상 DOM에 렌더링**한 뒤 CSS `display` 속성만 전환한다. 따라서 `v-if`는 초기 로드 비용이 낮지만 토글 비용이 높고, `v-show`는 초기 렌더링 비용이 높지만 토글 비용이 낮다. 콘텐츠를 매우 자주 전환해야 하는 경우에는 `v-show`를, 실행 중에 조건이 변경되지 않는 경우에는 `v-if`를 사용하는 것이 권장된다.

**29. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1점 | props는 부모→자식 하향식 단방향 바인딩(one-way-down binding)을 형성한다 |
| 2점 | 하위 컴포넌트가 실수로 상위 컴포넌트 상태를 변경해 데이터 흐름을 이해하기 어렵게 만드는 것을 방지 → 데이터 흐름의 "일관성"과 "단순화" |
| 1점 | 자식은 `$emit`(또는 `defineEmits`)으로 이벤트를 발신하고, 부모가 `v-on`으로 수신해 자신의 상태를 변경한다 |

**모범 답안**
> 모든 props는 자식과 부모 속성 사이에 **하향식 단방향 바인딩**을 형성한다. 이는 하위 컴포넌트가 실수로 상위 컴포넌트의 상태를 변경하여 앱의 데이터 흐름을 이해하기 어렵게 만드는 것을 방지하기 위한 설계로, 데이터 흐름의 **일관성과 단순화**를 목적으로 한다. 따라서 자식은 props를 직접 수정할 수 없고, `$emit(event, ...args)`으로 사용자 정의 이벤트를 발신해 부모에게 변경을 요청해야 한다. 부모는 `v-on`(`@some-event`)으로 이를 수신해 자신이 소유한 데이터를 변경하며, 그 결과가 다시 props를 통해 자식으로 내려간다.

**30. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1점 | `console.log('Hi')`가 Call Stack에서 실행되어 `Hi` 출력 |
| 1점 | `setTimeout`이 Call Stack에 올라간 뒤 **Web API로 위임**되어 타이머 시작 |
| 1점 | `console.log('Bye')`가 실행되어 `Bye` 출력 (타이머를 기다리지 않음) |
| 1점 | 3초 후 Web API가 콜백을 **Task Queue(FIFO)** 로 이동 → **Event Loop**가 Call Stack이 빈 것을 확인하고 push → `Work` 출력 |

**모범 답안**
> ① `console.log('Hi')`가 Call Stack(LIFO)에 들어가 즉시 실행되어 `Hi`가 출력된다. ② `setTimeout(myFunc, 3000)`이 Call Stack에 들어가지만, 시간이 소요되는 작업이므로 브라우저가 제공하는 **Web API**로 위임되고 3초 타이머가 시작된다. Call Stack에서는 곧바로 제거되므로 다음 코드가 실행된다. ③ `console.log('Bye')`가 Call Stack에 들어가 실행되어 `Bye`가 출력된다. ④ 3초가 지나면 Web API가 `myFunc`를 **Task Queue(FIFO)** 로 보낸다. ⑤ **Event Loop**가 Call Stack이 비어 있는지 지속적으로 확인하다가, 비어 있음을 확인하면 Task Queue에서 가장 오래된 작업인 `myFunc`를 Call Stack으로 push하고 실행하여 `Work`가 출력된다.

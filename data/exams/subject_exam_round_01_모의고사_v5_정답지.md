## 객관식 해설

**1. 정답 ②** — props는 부모 컴포넌트로부터 자식 컴포넌트로 데이터를 전달하는데 사용되는 속성이다. (5_vue_componentstateflow)

**2. 정답 ②** — 부모→자식은 props, 자식→부모는 $emit(이벤트 발신)으로 데이터/상태 변화를 전달한다.

**3. 정답 ③** — props는 하향식 단방향 바인딩이므로 자식에서 변경해도 부모에는 영향을 주지 않으며, 자식 내부에서의 props 변경 시도 자체가 허용되지 않는다.

**4. 정답 ②** — 모든 props는 자식 속성과 부모 속성 사이에 하향식 단방향 바인딩(one-way-down binding)을 형성한다.

**5. 정답 ②** — 단방향 데이터 흐름은 하위 컴포넌트가 실수로 상위 상태를 변경해 데이터 흐름을 이해하기 어렵게 만드는 것을 방지하기 위함이다.

**6. 정답 ②** — defineProps()는 부모가 내려보낸 props를 사용하기 위해 자식 컴포넌트에서 명시적으로 선언하는 함수다.

**7. 정답 ④** — defineProps()는 "문자열 배열"과 "객체" 선언 두 가지 방식만 존재한다.

**8. 정답 ②** — 문자열 배열 선언은 `defineProps(['myMsg'])` 형태이며, 문자열 요소의 이름이 전달된 props의 이름이 된다.

**9. 정답 ②** — 객체 선언에서 각 속성의 값은 데이터 타입에 해당하는 생성자 함수(Number, String 등)여야 한다.

**10. 정답 ②** — "❖ 객체 선언 문법 사용 권장"이 강조되어 있다.

**11. 정답 ④** — 객체 선언 문법의 장점은 문서화, 타입 경고, 유효성 검사이며 렌더링 속도 향상과는 무관하다.

**12. 정답 ②** — `required: true`는 문자열 타입이며 필수로 전달되어야 함을 의미한다.

**13. 정답 ①** — type이 Number, default가 10이므로 값이 없으면 기본값 10이 사용되는 숫자형 props이다.

**14. 정답 ②** — 자식 컴포넌트로 전달 시(`<ParentChild my-msg="message" />`)에는 kebab-case 표기가 권장된다.

**15. 정답 ②** — defineProps({ myMsg: String })와 `{{ myMsg }}` 처럼 선언·참조 시 camelCase를 사용한다.

**16. 정답 ②** — v-bind 없이 정적으로 작성한 값은 문자열 "1"을 전달하는 Static props이다.

**17. 정답 ②** — v-bind(:)를 사용하면 Dynamic props로 취급되어 숫자 1 자체가 전달된다.

**18. 정답 ①** — v-for와 :key, 동적 props(:my-prop="item")를 함께 사용하는 것이 옳은 형태다.

**19. 정답 ②** — '$' 표기는 Vue 인스턴스의 내부 변수(라이프사이클 훅, 인스턴스 메서드 등)에 접근함을 나타낸다.

**20. 정답 ②** — event는 커스텀 이벤트 이름, args는 추가 인자이다.

**21. 정답 ②** — $emit을 템플릿 표현식에서 직접 사용해 커스텀 이벤트를 발신할 수 있다.

**22. 정답 ②** — 부모는 v-on(@)을 사용하여 자식이 발신한 이벤트를 수신한다.

**23. 정답 ②** — defineEmits()로 발신할 이벤트를 명시적으로 선언한다.

**24. 정답 ①** — script에서는 $emit에 접근할 수 없기 때문에 defineEmits()가 이를 대신할 함수를 반환한다.

**25. 정답 ②** — 부모의 콜백 함수는 `(...args) => { console.log(args) }`처럼 rest parameter로 배열 형태로 수신한다.

**26. 정답 ③** — 선언·발신은 camelCase, 부모에서의 수신은 kebab-case를 사용한다.

**27. 정답 ②** — `click: null`처럼 값이 null이면 해당 이벤트에 유효성 검사가 없음을 의미한다.

**28. 정답 ②** — 유효성 검사 함수가 false를 반환하면 console.warn이 출력된다.

**29. 정답 ②** — computed()는 계산된 속성(computed property)을 정의하는 함수다.

**30. 정답 ②** — computed의 반환값은 computed ref이며 일반 refs처럼 .value로 참조한다.

**31. 정답 ②** — computed는 의존 데이터가 변경될 때만 재평가되어 캐시된 결과를 반환하지만, method는 호출할 때마다 항상 함수를 실행한다.

**32. 정답 ①** — Cache는 데이터를 일시적으로 저장해두고 다시 계산하지 않고 빠르게 접근하도록 하는 것을 의미한다.

**33. 정답 ②** — computed는 동일한 의존성을 가진 여러 곳에서 계산 결과를 캐싱해 중복 계산을 방지하는 데 유용하다.

**34. 정답 ②** — method는 데이터 의존 여부와 무관하게 항상 같은 로직을 실행하는 함수를 정의할 때 적절하다.

**35. 정답 ①** — watch()는 하나 이상의 반응형 데이터를 감시하고, 변경되면 콜백 함수를 호출한다.

**36. 정답 ②** — newValue는 필수이고, oldValue는 optional이다.

**37. 정답 ②** — 배열을 활용해 `watch([foo, bar], ([newFoo, newBar], [prevFoo, prevBar]) => {...})` 형태로 여러 source를 동시에 감시한다.

**38. 정답 ③** — computed와 watch 모두 의존(감시)하는 원본 데이터를 직접 변경하지 않는다는 것이 슬라이드의 강조 원칙이다.

**39. 정답 ②** — Watchers는 DOM 변경, 비동기 작업, 외부 API 연동 같은 side-effect 작업에 사용된다.

**40. 정답 ③** — reverse()/sort()는 원본 배열을 변경하므로 `[...numbers].reverse()`처럼 복사본을 만들어 처리해야 한다.

## 서술형 채점 기준

### 61. Props와 $emit을 이용한 부모-자식 컴포넌트 간 데이터 흐름 (4점)

| 배점 | 채점 요소                                                                                   |
| ---- | ------------------------------------------------------------------------------------------- |
| 1점  | props는 부모→자식으로 데이터를 전달하는 하향식 단방향 바인딩임을 서술                       |
| 1점  | 부모 값 변경 시 자식에 자동 반영되나 역방향은 불가함을 서술                                 |
| 1점  | 자식→부모는 $emit(또는 defineEmits)으로 커스텀 이벤트를 발신함을 서술                       |
| 1점  | 부모는 v-on(@)으로 이벤트를 수신하며, 이 구조로 데이터 흐름의 일관성/단순성이 유지됨을 서술 |

**모범 답안:** 부모 컴포넌트는 props를 통해 자식 컴포넌트로 데이터를 전달하며, 이는 하향식 단방향 바인딩(one-way-down binding)으로 부모의 값이 변경되면 자식에 자동으로 반영되지만 그 반대는 불가능하다. 반대로 자식 컴포넌트에서 어떤 일이 발생했음을 부모에게 알리고 싶을 때는 $emit(또는 defineEmits로 정의한 emit 함수)을 사용해 커스텀 이벤트를 발신하고, 부모는 v-on(@)으로 이를 수신하여 콜백 함수를 실행한다. 이렇게 데이터는 부모→자식으로만 내려가고, 자식→부모로는 이벤트를 통해 알리는 방식으로 데이터 흐름의 일관성과 단순성을 유지한다.

### 62. props 단방향 설계 이유와 자식의 부모 데이터 직접 변경 시 문제 (4점)

| 배점 | 채점 요소                                                                |
| ---- | ------------------------------------------------------------------------ |
| 1점  | 하위 컴포넌트의 실수로 인한 상위 상태 변경 방지가 목적임을 서술          |
| 1점  | 데이터 흐름 추적/유지보수가 어려워지는 문제를 서술                       |
| 1점  | Vue가 자식 내부에서의 props 변경 시도를 막고 있음을 서술                 |
| 1점  | 부모 데이터를 바꾸려면 $emit으로 요청하고 부모가 직접 변경해야 함을 서술 |

**모범 답안:** props를 단방향으로 설계한 이유는 하위 컴포넌트가 실수로 상위 컴포넌트의 상태를 변경하여 애플리케이션의 데이터 흐름을 이해하기 어렵게 만드는 것을 방지하기 위해서이다. 만약 자식이 부모의 상태를 자유롭게 변경할 수 있다면 어떤 컴포넌트가 언제 데이터를 바꾸는지 추적하기 어려워져 유지보수가 힘들어진다. 그래서 Vue는 자식 컴포넌트 내부에서 props를 변경하려는 시도를 원천적으로 막고 있으며, 자식이 부모 데이터를 바꾸고 싶다면 $emit을 통해 부모에게 요청하고 부모가 직접 자신의 데이터를 변경하도록 유도한다.

### 63. defineProps() 문자열 배열 vs 객체 선언 비교 (4점)

| 배점 | 채점 요소                                           |
| ---- | --------------------------------------------------- |
| 1점  | 문자열 배열 선언 방식(이름만 지정)을 설명           |
| 1점  | 객체 선언 방식(키=이름, 값=타입 생성자 함수)을 설명 |
| 1점  | 문서화 및 타입 경고 이점을 서술                     |
| 1점  | required/default 등 유효성 검사 활용 이점을 서술    |

**모범 답안:** 문자열 배열 선언(`defineProps(['myMsg'])`)은 문자열 요소의 이름이 곧 전달받을 props의 이름이 되는 간단한 방식이다. 반면 객체 선언(`defineProps({ myMsg: String })`)은 각 속성의 키가 props 이름이고, 값은 해당 props의 데이터 타입에 해당하는 생성자 함수여야 한다. 슬라이드에서는 객체 선언 문법을 권장하는데, 그 이유는 컴포넌트를 가독성 좋게 문서화할 수 있고, 다른 개발자가 잘못된 타입의 값을 전달했을 때 브라우저 콘솔에 경고를 출력해주며, required나 default 같은 옵션으로 props에 대한 유효성 검사로도 활용할 수 있기 때문이다.

### 64. Props/Event Casing 규칙과 존재 이유 (4점)

| 배점 | 채점 요소                                                       |
| ---- | --------------------------------------------------------------- |
| 1점  | Props: 템플릿 전달 시 kebab-case, 선언/참조 시 camelCase를 서술 |
| 1점  | Event: 선언/발신 시 camelCase, 부모 수신 시 kebab-case를 서술   |
| 1점  | HTML 속성이 대소문자를 구분하지 않는다는 이유를 서술            |
| 1점  | script/JS 관례를 따르는 영역과 템플릿/HTML 영역의 구분을 설명   |

**모범 답안:** Props는 자식 컴포넌트로 전달하는 템플릿(HTML 속성) 표기 시에는 kebab-case(`my-msg`)를, 선언(defineProps)과 템플릿 내부 참조 시에는 camelCase(`myMsg`)를 사용한다. Event 역시 선언(defineEmits)과 script에서의 발신(emit) 시에는 camelCase(`someEvent`)를, 부모 컴포넌트에서 v-on으로 수신할 때는 kebab-case(`@some-event`)를 사용한다. 이는 HTML 속성이 대소문자를 구분하지 않기 때문에 HTML/템플릿 표기 영역에서는 kebab-case를, JavaScript 변수/함수명 관례를 따르는 script 영역에서는 camelCase를 사용하도록 구분한 것이다.

### 65. Static Props vs Dynamic Props (3점)

| 배점 | 채점 요소                                               |
| ---- | ------------------------------------------------------- |
| 1점  | Static props 정의와 예시(문자열 그대로 전달)            |
| 1점  | Dynamic props 정의와 예시(v-bind로 표현식 결과 전달)    |
| 1점  | 동일한 값이라도 v-bind 여부에 따라 타입이 달라짐을 서술 |

**모범 답안:** Static(정적) props는 v-bind 없이 일반 HTML 속성처럼 값을 그대로 문자열로 전달하는 방식이다. 예를 들어 `<SomeComponent num-props="1" />`은 문자열 "1"을 전달한다. 반면 Dynamic(동적) props는 v-bind(:)를 사용하여 JavaScript 표현식의 결과값을 그대로 전달하는 방식으로, `<SomeComponent :num-props="1" />`은 숫자 1 자체를 전달한다. 즉 같은 값 1을 쓰더라도 v-bind 사용 여부에 따라 문자열로 전달되는지 원래 타입(숫자, 객체 등)으로 전달되는지가 달라진다.

### 66. Computed vs Method — 캐싱 관점 (4점)

| 배점 | 채점 요소                                                          |
| ---- | ------------------------------------------------------------------ |
| 1점  | computed는 의존 데이터를 기반으로 결과를 캐싱함을 서술             |
| 1점  | 데이터가 바뀌지 않으면 재계산 없이 이전 결과를 반환함을 서술       |
| 1점  | method는 호출/렌더링마다 항상 함수를 실행하며 캐싱되지 않음을 서술 |
| 1점  | 각각 적절한 사용 상황(재사용 계산 vs 단순 동작 수행)을 서술        |

**모범 답안:** computed 속성은 의존하는 반응형 데이터를 기반으로 결과를 캐시(cache)하며, 의존하는 데이터가 변경된 경우에만 재평가된다. 따라서 같은 computed를 여러 번 참조해도 데이터가 바뀌지 않았다면 이전에 계산된 결과를 즉시 반환하여 불필요한 재계산을 막는다. 반면 method는 호출될 때마다, 즉 컴포넌트가 다시 렌더링될 때마다 항상 함수를 실행하며 캐싱되지 않는다. 따라서 동일한 의존성을 가진 계산 결과를 여러 곳에서 재사용하며 성능을 아끼고 싶다면 computed가 적절하고, 단순히 특정 동작을 수행하거나 데이터 의존 여부와 무관하게 항상 같은 로직을 실행해야 한다면 method가 적절하다.

### 67. Computed vs Watchers — 목적/동작 비교 (4점)

| 배점 | 채점 요소                                                                    |
| ---- | ---------------------------------------------------------------------------- |
| 1점  | Computed는 계산된 값을 반환하는 데 초점이 있음을 서술                        |
| 1점  | Watchers는 데이터 변화를 감시해 side-effect를 수행하는 데 초점이 있음을 서술 |
| 1점  | 각각의 사용 예시(길이/필터링 계산 vs DOM 변경·비동기·API 연동)를 서술        |
| 1점  | 공통점(변화 감지, 원본 데이터 직접 변경 금지)을 서술                         |

**모범 답안:** Computed는 의존하는 데이터 속성을 기반으로 "계산된 값을 반환"하는 데 초점이 있으며, 계산한 값을 캐싱하여 재사용함으로써 중복 계산을 방지한다. 연산된 길이나 필터링된 목록 계산처럼 값 자체를 얻는 데 사용한다. 반면 Watchers는 특정 데이터 속성의 변화를 감시하다가 변화가 생기면 side-effect(부수 효과) 작업을 수행하는 데 초점이 있다. DOM 변경, 비동기 작업 수행, 외부 API와의 연동처럼 값을 반환하기보다는 어떤 동작을 실행해야 할 때 사용한다. 다만 둘 다 데이터의 변화를 감지하고 처리한다는 공통점이 있으며, 의존(감시)하는 원본 데이터를 직접 변경하지 않는다는 원칙은 동일하게 적용된다.

### 68. computed 사용 시 주의사항 두 가지 (4점)

| 배점 | 채점 요소                                                |
| ---- | -------------------------------------------------------- |
| 1점  | 반환 값을 읽기 전용 snapshot으로 취급해야 함을 서술      |
| 1점  | 새 값을 원하면 원본 데이터를 업데이트해야 함을 서술      |
| 1점  | reverse()/sort() 등이 원본 배열을 변경하는 문제를 서술   |
| 1점  | `[...numbers].reverse()`처럼 복사본을 사용해야 함을 서술 |

**모범 답안:** 첫째, computed의 반환 값은 의존하는 데이터로부터 파생된 일종의 snapshot이며 읽기 전용으로 취급되어야 한다. 새 값을 얻고 싶다면 computed의 반환 값을 직접 수정할 것이 아니라 의존하는 원본 데이터를 업데이트해야 한다. 둘째, computed 내부에서 reverse()나 sort()처럼 원본 배열 자체를 변경하는 메서드를 사용하면 안 되며, `return numbers.reverse()`처럼 작성하면 원본 배열이 변경되어 버린다. 대신 `return [...numbers].reverse()`처럼 전개 연산자로 복사본을 만든 뒤 그 복사본에 대해 연산을 수행해야 원본 데이터를 안전하게 보존할 수 있다.

### 69. onMounted / onUpdated 역할과 동기적 작성 조건 (3점)

| 배점 | 채점 요소                                                         |
| ---- | ----------------------------------------------------------------- |
| 1점  | onMounted의 역할(초기 렌더링/DOM 마운트 시점 로직) 서술           |
| 1점  | onUpdated의 역할(반응형 데이터 변경에 따른 재렌더링 후 로직) 서술 |
| 1점  | hooks 함수가 동기적으로 작성되어야 인스턴스와 자동 연결됨을 서술  |

**모범 답안:** onMounted는 컴포넌트가 초기 렌더링되어 실제 DOM에 마운트된 시점에 실행할 로직을 등록하는 훅이고, onUpdated는 반응형 데이터의 변경으로 컴포넌트의 DOM이 다시 렌더링/업데이트된 후 실행할 로직을 등록하는 훅이다. 예를 들어 `onMounted(() => { console.log('mounted') })`처럼 사용한다. Vue는 이러한 Lifecycle Hooks에 등록된 콜백 함수들을 해당 컴포넌트 인스턴스와 자동으로 연결해 주는데, 이 연결이 올바르게 동작하려면 hooks 함수들은 반드시 동기적으로 작성되어야 한다.

### 70. Virtual DOM 개념·장점과 실제 DOM 접근 권장 방법 (4점)

| 배점 | 채점 요소                                                                       |
| ---- | ------------------------------------------------------------------------------- |
| 1점  | Virtual DOM 개념(메모리 상의 가상 DOM, 실제 DOM과 diff 후 변경분만 반영)을 서술 |
| 1점  | 장점(효율성, 반응성, 추상화) 중 최소 2가지 이상 서술                            |
| 1점  | querySelector 등 직접 DOM 접근을 지양해야 함을 서술                             |
| 1점  | ref 속성 + ref(null) + onMounted 등 lifecycle hook 안에서 접근하는 방식을 서술  |

**모범 답안:** Virtual DOM은 가상의 DOM을 메모리에 저장하고 실제 DOM과 동기화하는 프로그래밍 개념으로, 실제 DOM과의 변경 사항을 비교(diff)하여 변경된 부분만 실제 DOM에 적용함으로써 웹 애플리케이션의 성능을 향상시키는 Vue의 내부 렌더링 기술이다. 이를 통해 효율성(실제 DOM 조작 최소화), 반응성(데이터 변경 감지 및 UI 자동 갱신), 추상화(개발자가 DOM 조작을 직접 다루지 않고 컴포넌트/템플릿 중심으로 개발 가능)라는 장점을 얻는다. 다만 querySelector, createElement, addEventListener 같은 JavaScript의 DOM 접근 메서드로 실제 DOM에 직접 접근하는 것은 지양해야 하며, 부득이하게 특정 DOM 엘리먼트에 직접 접근해야 한다면 템플릿에 ref 속성을 부여하고, script에서 동일한 이름의 `ref(null)` 변수를 선언한 뒤 onMounted 등의 Lifecycle Hooks 안에서 접근하는 간접적인 방식을 사용해야 한다.

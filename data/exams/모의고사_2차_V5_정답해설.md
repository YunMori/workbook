## Ⅰ. 객관식 해설

**1. 정답 ④** — 템플릿 리터럴은 **ES6+** 부터 지원된다. (DOM_Event §3)

**2. 정답 ①** — 객체의 `key`는 **문자형만** 허용되고 `value`는 모든 자료형이 허용된다. 띄어쓰기 같은 구분자가 있는 key는 **대괄호 접근만** 가능하다. (Asynchronous_JavaScript — 객체 구조)

**3. 정답 ③** — `for...in`은 속성 열거를 사용하므로 특정 순서를 보장하지 않고 인덱스가 출력된다. 인덱스 순서가 중요한 배열에서는 `for` 또는 `for...of`를 사용해야 한다. (DOM_Event §6)

**4. 정답 ②** — `preventDefault()`는 해당 이벤트의 **기본 동작을 실행하지 않도록** 지정한다(예: form 제출 시 새로고침 방지, `<a>` 클릭 시 페이지 이동 방지). (DOM_Event §9)

**5. 정답 ④** — input 이벤트 핸들러에서 입력값은 `event.currentTarget.value`로 접근한다. (DOM_Event §9)

**6. 정답 ①** — `v-bind`로 바인딩한 값이 `null`이나 `undefined`이면 해당 속성이 렌더링 요소에서 **제거된다**. (Basic_Syntax — Attribute Bindings)

**7. 정답 ③** — Key Modifiers를 사용해 `@keyup.enter="onSubmit"`로 작성한다. (Basic_Syntax — Key Modifiers)

**8. 정답 ②** — `v-if`는 Cheap initial load / expensive toggle, `v-show`는 Expensive initial load / cheap toggle. 초기 조건이 false일 때 아무 작업도 하지 않는 쪽은 `v-if`다. (Basic_Syntax — v-if와 v-show)

**9. 정답 ①** — `v-model` 표현식의 초기 값이 어떤 `option`과도 일치하지 않으면 `select` 요소는 **"선택되지 않은(unselected)" 상태**로 렌더링된다. (Basic_Syntax — `<select>` 활용)

**10. 정답 ④** — `sort()`와 `reverse()`는 **변화 메서드**로 원본 배열을 변경한다. `computed` 안에서는 `[...numbers].reverse()`처럼 복사본을 만들어 사용해야 한다. (Basic_Syntax 참고 / component_state_flow §4-3)

**11. 정답 ②** — 모든 App에는 다른 컴포넌트들을 하위로 포함하는 **Root(최상위) 컴포넌트가 하나** 필요하다. (Introduction_of_Vue §3-1, §4-1)

**12. 정답 ③** — Bundler의 역할에는 의존성 관리뿐 아니라 **코드 최적화, 리소스 관리** 등이 포함된다. (Introduction_of_Vue §6)

**13. 정답 ④** — `<script setup>`에서 선언된 변수·함수는 템플릿에서 **자동으로 사용 가능**하므로 별도의 `return`이 필요 없다. (`return`이 필요한 것은 CDN 방식의 `setup()` 함수) (Introduction_of_Vue §4-2)

**14. 정답 ①** — `<style scoped>`는 해당 컴포넌트 내부의 스타일이 **현재 컴포넌트 내부 요소에게만 적용**되도록 범위를 제한한다. (Introduction_of_Vue §13)

**15. 정답 ②** — 객체 선언 문법을 권장하는 이유는 문서화, 잘못된 유형 전달 시 콘솔 경고, 유효성 검사 활용이다. 코드 길이는 오히려 배열 선언이 짧다. (component_state_flow §2-7)

**16. 정답 ③** — `default`가 지정된 prop은 값이 전달되지 않으면 기본값이 사용되는 것이므로, **필수(`required: true`)와는 다른** 개념이다. (component_state_flow §2-7)

**17. 정답 ④** — `computed`의 반환 값은 의존 데이터로부터 파생된 일종의 **snapshot**이며 읽기 전용으로 취급해야 한다. 새 값을 얻으려면 의존하는 데이터를 업데이트해야 한다. (component_state_flow §4-3)

**18. 정답 ①** — `<script>` 내부에서 ref 값을 변경하려면 `.value`가 필요하다. (component_state_flow §4-1)

**19. 정답 ③** — Pinia를 사용한다고 해서 모든 데이터를 하나의 store에 넣어야 하는 것은 아니며, **데이터의 주체별로 나눠서 저장**하고 `pass props`·`emit event`와 함께 사용해야 한다. (state_management — 참고)

**20. 정답 ②** — `RouterLink`를 클릭했을 때 내부적으로 호출되는 메서드가 `router.push()`이므로, `RouterLink` 클릭 == `router.push()` 호출이다. (state_management — Programmatic Navigation)

**21. 정답 ④** — Axios는 **브라우저를 위한 XHR 객체를 생성**하는 라이브러리로, 주로 웹 애플리케이션에서 서버와 통신할 때 사용한다. (Asynchronous_JavaScript — Axios)

## Ⅱ. 주관식 해설

**22.** `index` / `key`, `index`
```html
<div v-for="(item, index) in arr"></div>
<div v-for="(value, key, index) in object"></div>
```
- 배열은 `(요소, 인덱스)`, 객체는 `(값, 키, 인덱스)` 순서다.

**23.** ㉠ `open` / ㉡ `send`
```js
xhr.open('GET', 'https://jsonplaceholder.typicode.com/posts')
xhr.send()
```

**24.**
- 플러그인 이름: **`pinia-plugin-persistedstate`**
- 옵션: `defineStore()`의 **3번째 인자**로 `{ persist: true }` 추가
```js
export const useCounterStore = defineStore('counter', () => {
  ...
  return { count, doubleCount, increment }
}, { persist: true })
```

**25.** `{ name, age, city }`
```js
function printInfo({ name, age, city }) {
  console.log(`이름: ${name}, 나이: ${age}, 도시: ${city}`)
}
```
- 함수 호출 시 객체를 구조 분해하여 매개변수로 전달받는 방식이다.

**26.**
1. **computed의 반환 값은 변경하지 말 것** — 계산된 값은 의존 데이터로부터 파생된 snapshot이며 읽기 전용으로 취급해야 한다. 새 값이 필요하면 의존하는 데이터를 업데이트한다.
2. **computed 사용 시 원본 배열을 변경하지 말 것** — `reverse()`, `sort()`는 원본을 변경하므로 `[...numbers].reverse()`처럼 복사본을 만들어 사용한다.

**27.**
- Call Stack: **LIFO** (Last In First Out)
- Task Queue: **FIFO** (First In First Out)

## Ⅲ. 서술형 채점 기준

**28. (5점)**

| 배점 | 채점 요소 |
|---|---|
| 2점 | `ref()`는 반응형 상태(데이터)를 선언하는 함수이며, 인자를 `.value` 속성이 있는 **ref 객체로 래핑하여 반환**한다(ref === reactive reference). 인자는 어떤 타입도 가능 |
| 1점 | `ref`로 선언된 변수의 값이 변경되면 이를 사용하는 템플릿이 자동으로 업데이트된다 |
| 2점 | `<script>`에서는 `.value`로 접근해야 하지만, 템플릿에서는 **자동으로 언래핑(automatically unwrapped)** 되므로 `.value`를 쓸 필요가 없다 |

**모범 답안**
> `ref()`는 반응형 상태(데이터)를 선언하는 함수로, 전달한 인자를 `.value` 속성을 가진 **ref 객체로 래핑하여 반환**한다(ref === reactive reference). 인자로는 어떤 타입도 가능하며, `ref`로 선언된 변수의 값이 변경되면 그 값을 사용하는 템플릿이 자동으로 업데이트된다. `<script>` 내부에서는 ref 객체 자체가 반환되므로 실제 값을 읽거나 쓰려면 반드시 `message.value`처럼 `.value`로 접근해야 한다. 반면 템플릿에서는 편의상 `.value`가 **자동으로 언래핑(automatically unwrapped)** 되기 때문에 `{{ message }}`처럼 바로 사용할 수 있다. 이렇게 객체로 감싸는 이유는 JavaScript에서 일반 변수의 접근이나 변형을 감지할 방법이 없어, 의존성 추적 기반 반응형 시스템을 구현하려면 참조 자료형이 필요하기 때문이다.

---

**29. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1.5점 | 대응 관계 3개: `state === ref()`, `getters === computed()`, `actions === function()` |
| 1.5점 | `getters`는 state를 기반으로 계산된 값을 반환(computed와 동일) |
| 1점 | `actions`는 getters와 달리 **state 조작, 비동기, API 호출** 등 다른 로직을 진행할 수 있음 |

**모범 답안**
> Pinia의 store는 `state`, `getters`, `actions`로 이루어지며, 각각 Vue Composition API의 `ref()`, `computed()`, `function()`과 동일하다. `state`는 반응형 상태(데이터)로 `ref()`로 선언하고, 컴포넌트 깊이에 관계없이 store 인스턴스를 통해 직접 읽고 쓸 수 있다. `getters`는 `computed()`로 정의하는 **계산된 값**으로, state에 의존해 파생된 값을 반환하며 의존 데이터가 변경될 때만 재평가된다. `actions`는 일반 함수로 정의하는 메서드로, `getters`와 달리 **state 조작, 비동기 처리, API 호출** 등 다른 로직까지 수행할 수 있다는 점이 가장 큰 차이다. 즉 getters는 "읽어서 계산해 돌려주는" 역할, actions는 "상태를 바꾸거나 외부와 통신하는" 역할을 담당한다. 단, Setup Store에서는 이들을 사용하려면 반드시 `return`으로 반환해야 한다.

---

**30. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1점 | 동기 = 하나의 작업이 완료된 후 다음 작업 실행 / 비동기 = 작업 완료를 기다리지 않고 다음 작업 실행 |
| 1.5점 | 동기식 문제: 특정 로직이 실행되는 동안 다른 로직 실행을 차단 → 앱이 멈춘 듯한, 응답하지 않는 사용자 경험 (예: 아주 큰 데이터를 모두 불러온 뒤에야 앱 로직 수행) |
| 1.5점 | 비동기 이점: 먼저 처리되는 부분부터 보여줄 수 있어 UX에 긍정적. 시간이 걸리는 작업은 별도 요청 후 응답이 빨리 오는 작업부터 처리 |

**모범 답안**
> 동기(Synchronous) 처리는 프로그램의 실행 흐름이 순차적으로 진행되어 하나의 작업이 완료된 후에야 다음 작업이 실행되는 방식이고, 비동기(Asynchronous) 처리는 작업이 완료되기를 기다리지 않고 다음 작업을 실행하는 방식이다. 예를 들어 아주 큰 데이터를 불러온 뒤 실행되는 앱을 동기식으로 처리하면, 데이터를 모두 불러온 뒤에야 앱의 실행 로직이 수행되므로 사용자는 그동안 마치 **앱이 멈춘 것과 같은 경험**을 겪게 된다. 즉 동기식 처리는 특정 로직이 실행되는 동안 다른 로직의 실행을 차단하기 때문에 프로그램이 응답하지 않는 듯한 사용자 경험을 만든다. 반면 비동기로 처리하면 시간이 오래 걸리는 작업은 별도로 요청을 보낸 뒤 응답이 빨리 오는 작업부터 처리하므로, **먼저 처리되는 부분부터 사용자에게 보여줄 수 있어** 사용자 경험에 긍정적인 효과를 준다. 이와 같은 이유로 많은 웹 기능이 비동기 로직으로 구현된다.

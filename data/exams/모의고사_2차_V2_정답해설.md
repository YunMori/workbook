## Ⅰ. 객관식 해설

**1. 정답 ④** — `kebab-case`는 HTML에서 사용한다. HTML은 대소문자를 구분하지 않아(전부 소문자로 처리) camelCase를 쓸 수 없기 때문이다. JavaScript 함수명에는 camelCase를 쓴다. (DOM_Event §2)

**2. 정답 ②** — 원시 자료형은 변수에 **값이 직접 저장**되고 값이 복사(불변), 참조 자료형은 **주소가 저장**되고 주소가 복사(가변)된다. `Array`, `Function`, `Object`는 참조 자료형이다. (DOM_Event §3)

**3. 정답 ①** — `==`는 암묵적 타입 변환 후 값 비교(`'1'==1` → true, `0==false` → true), `===`는 값과 타입 모두 비교(둘 다 false). (실행 검증 완료) (DOM_Event §4)

**4. 정답 ③** — `querySelectorAll()`은 CSS selector를 만족하는 **NodeList**를 반환한다. `querySelector()`는 조건에 맞는 **첫 번째 요소 한 개**를 반환하며, `querySelectorAll()`이 반환하는 NodeList는 DOM 변경사항을 실시간 반영하지 않는 **정적** 목록이다. (DOM_Event §7)

**5. 정답 ④** — `classList.toggle()`은 클래스가 존재하면 제거 후 `false` 반환, 없으면 추가 후 `true` 반환. (DOM_Event §7)

**6. 정답 ②** — 콧수염 구문은 데이터를 일반 텍스트로 해석하므로, 실제 HTML을 출력하려면 `v-html`을 사용해야 한다. (Basic_Syntax — Raw HTML)

**7. 정답 ①** — 각 바인딩에는 **하나의 단일 표현식**만 포함될 수 있다(`return` 뒤에 쓸 수 있는 코드). `if` 문은 표현식이 아니므로 작동하지 않는다. (Basic_Syntax — JavaScript Expressions)

**8. 정답 ③** — 피해야 할 `key` 값은 **배열 인덱스(ㄴ)** 와 **객체 자체(ㄹ)**. 권장되는 값은 DB 고유 ID, UUID 등 고유 식별자다. (Basic_Syntax — v-for with key)

**9. 정답 ②** — 여러 체크박스에 배열을 `v-model`로 바인딩하면, 해당 배열에 현재 선택된 체크박스의 `value`들이 담긴다. (Basic_Syntax — v-model 활용)

**10. 정답 ④** — Modifiers는 chained 되게 작성할 수 있으며 **작성된 순서로 실행**되므로 순서에 유의해야 한다. (Basic_Syntax — Event Modifiers)

**11. 정답 ③** — ③은 **MPA(Multi Page Application)** 에 대한 설명이다. SPA는 페이지 전체를 다시 로드하지 않는다. (Introduction_of_Vue §1-2)

**12. 정답 ①** — Vite는 **Rollup**이라는 Bundler를 사용한다. (Introduction_of_Vue §6, §7)

**13. 정답 ④** — Composition API는 `import`해서 가져온 API 함수들로 로직을 정의하며 Vue3의 권장 방식이다. Option API는 Vue2의 작성 방식이지만 Vue3에서도 여전히 지원된다. (Introduction_of_Vue §10)

**14. 정답 ②** — `<style>`에 `scoped`를 붙이지 않으면 해당 스타일이 **전역(모든 컴포넌트)** 에 영향을 미친다. (Introduction_of_Vue §13)

**15. 정답 ③** — `defineProps()`는 문자열 배열 선언과 객체 선언 2가지가 있으며, **객체 선언 문법 사용이 권장**된다. 객체 선언 시 값은 데이터 타입에 해당하는 생성자 함수(`String`, `Number` 등)여야 한다. (component_state_flow §1-2)

**16. 정답 ①** — `<script setup>` 내부에서는 `$emit` 메서드에 접근할 수 없기 때문에, `defineEmits()`가 `$emit` 대신 사용할 수 있는 **동등한 함수를 반환**한다. (component_state_flow §2-3)

**17. 정답 ③** — `oldValue`는 **optional**(선택 인자)이다. (component_state_flow §4-1)

**18. 정답 ④** — computed는 계산한 값을 캐싱해 재사용하고 중복 계산을 방지하며, watch는 데이터 변화에 따른 특정 작업(DOM 변경, 비동기 작업, 외부 API 연동 등 side-effect)을 수행한다. 둘 다 원본 데이터를 직접 변경하지 않는다(② 오답). (component_state_flow §4-2)

**19. 정답 ②** — Local Storage는 쿠키와 **다르게** 네트워크 요청 시 서버로 전송되지 않는다. (state_management — Local Storage)

**20. 정답 ①** — Named Routes의 장점은 하드 코딩된 URL을 쓰지 않아도 되고, URL 입력 시 오타를 방지할 수 있다는 것이다. (state_management — Named Routes)

**21. 정답 ③** — `XMLHttpRequest`는 이름에 XML이 들어가지만 XML뿐 아니라 **모든 종류의 데이터**를 가져올 수 있다. (Asynchronous_JavaScript — AJAX)

## Ⅱ. 주관식 해설

**22.** `성인`
- `age`가 20이므로 `age >= 18`이 `true` → `expression1`인 `'성인'`이 반환된다.

**23.** `[1, 2, [3, 4, 5]]` / `[1, 2, []]`
- 나머지 매개변수는 남는 인자를 **배열**로 모은다. 인자가 부족하면 빈 배열 `[]`이 된다. (실행 검증 완료)

**24.** `onMounted`, `onUpdated`, `onUnmounted`

**25.**
- `num-props="1"` → **String**(문자열 `"1"`) — 정적 props
- `:num-props="1"` → **Number**(숫자 `1`) — 동적 props(`v-bind`)

**26.** `src/` 경로
- `@`는 `src/` 디렉토리를 뜻하는 약어다. `'@/components/MyComponent.vue'` === `'./src/components/MyComponent.vue'`

**27.** `{ a: 1, b: 2, c: 3, d: 4, e: 5 }`
- 객체 전개 구문은 객체를 **얕은 복사**하여 펼친다. 작성한 순서대로 `a` → `obj`의 속성들 → `e`가 배치된다. (실행 검증 완료)

## Ⅲ. 서술형 채점 기준

**28. (5점)**

| 배점 | 채점 요소 |
|---|---|
| 2점 | `computed`는 의존된 반응형 데이터를 기반으로 **캐시**되어, 의존 데이터가 변경된 경우에만 재평가된다 |
| 1점 | `method`는 다시 렌더링이 발생할 때마다 **항상 함수를 실행**한다 |
| 1점 | 캐시 = 데이터/결과를 일시적으로 저장해 다시 계산하지 않고 빠르게 접근하게 하는 임시 저장소 |
| 1점 | 사용처 구분: computed는 의존 데이터에 따라 결과가 바뀌는 계산된 속성 및 여러 곳에서 재사용할 때 / method는 단순히 특정 동작을 수행할 때 |

**모범 답안**
> `computed` 속성은 의존된 반응형 데이터를 기반으로 **캐시(cache)** 된다. 캐시란 데이터나 결과를 일시적으로 저장해 두어 같은 결과를 다시 계산하지 않고 빠르게 접근할 수 있게 하는 임시 저장소로, 의존하는 데이터가 변경되지 않는 한 이미 계산된 결과를 즉시 반환한다. 반면 `method` 호출은 다시 렌더링이 발생할 때마다 항상 함수를 실행하므로, 동일한 계산이 여러 곳에서 반복되면 불필요한 연산이 누적된다. 따라서 의존하는 데이터에 따라 결과가 바뀌고 여러 곳에서 재사용되는 계산된 값은 `computed`로, 단순히 특정 동작을 수행하거나 데이터 의존 여부와 무관하게 항상 같은 결과를 반환하는 함수는 `method`로 작성하는 것이 적절하다.

**29. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1점 | 상황 ①: 여러 뷰가 동일한 상태에 종속되는 경우 → 공유 상태를 공통 조상으로 "끌어올려" props로 전달하나, 계층이 깊어지면 비효율적 |
| 1점 | 상황 ②: 서로 다른 뷰의 기능이 동일한 상태를 변경해야 하는 경우 → emit으로 상태 복사본을 동기화하나 패턴이 깨지기 쉬움 |
| 2점 | 해결: 공유 상태를 추출해 전역에서 참조 가능한 중앙 저장소에서 관리 → 컴포넌트 트리 계층과 무관하게 상태 접근·기능 사용 가능 (단, 데이터의 주체별로 나눠 저장) |

**모범 답안**
> 컴포넌트 자체의 상태 관리는 단순하지만, **여러 컴포넌트가 상태를 공유할 때** 단순성이 무너진다. 첫째, 여러 뷰가 동일한 상태에 종속되는 경우 공유 상태를 공통 조상 컴포넌트로 끌어올린 뒤 props로 전달해야 하는데, 계층 구조가 깊어지면 비효율적이고 관리가 어려워진다. 둘째, 서로 다른 뷰의 기능이 동일한 상태를 변경해야 하는 경우 emit된 이벤트로 상태의 여러 복사본을 변경·동기화해야 하는데, 이 패턴은 깨지기 쉽고 유지 관리가 어려운 코드가 된다. Pinia는 각 컴포넌트의 공유 상태를 추출해 **전역에서 참조할 수 있는 중앙 저장소**에서 관리한다. 그 결과 컴포넌트 트리는 하나의 큰 View가 되고, 모든 컴포넌트가 트리 계층 구조와 관계없이 상태에 접근하거나 기능을 사용할 수 있다. 단, 모든 데이터를 하나의 저장소에 넣는 것이 아니라 데이터의 주체별로 나눠서 저장해야 한다.

**30. (4점)**

| 배점 | 채점 요소 |
|---|---|
| 1.5점 | 버블링 = 한 요소에 이벤트가 발생하면 그 요소의 핸들러가 동작하고, 이어서 부모 요소의 핸들러가 최상단 조상(document)까지 차례로 동작하는 현상 |
| 1.5점 | 이벤트 위임: 각 요소마다 핸들러를 붙이는 대신 **공통 조상 요소에 핸들러 하나만** 할당해 여러 요소를 한꺼번에 처리 |
| 1점 | `currentTarget` = 핸들러가 연결된 요소(=this), `target` = 실제 이벤트가 시작된 가장 안쪽 요소(버블링이 진행되어도 변하지 않음) |

**모범 답안**
> 버블링이란 한 요소에서 이벤트가 발생하면 그 요소에 할당된 핸들러가 먼저 동작하고, 이어서 부모 요소의 핸들러가 동작하며 최상단 조상 요소(`document`)를 만날 때까지 이 과정이 반복되는 현상이다. 예를 들어 `form > div > p` 구조에서 `<p>`만 클릭해도 p → div → form 순서로 세 핸들러가 모두 실행된다. 이 성질을 이용하면 각자 다른 동작을 하는 버튼이 여러 개 있을 때 버튼마다 핸들러를 붙이는 대신 **공통 조상 요소에 핸들러를 하나만 할당**해 여러 요소를 한꺼번에 다룰 수 있다. 이때 `event.currentTarget`은 항상 핸들러가 연결된 요소(공통 조상)를 참조하고 일반 함수 콜백의 `this`와 같은 반면, `event.target`은 실제로 이벤트가 시작된 가장 안쪽 요소를 참조하며 버블링이 진행되어도 변하지 않는다. 따라서 조상에 붙인 핸들러 안에서 `event.target`을 확인하면 어떤 버튼이 눌렸는지 식별할 수 있다.
